# Run Outcome Model

This document defines the canonical execution-truth contract for TranscriptX.

## Status Vocabulary (API-level)

Canonical consumer-facing statuses are:

- `requested`
- `enabled`
- `blocked`
- `skipped`
- `failed`
- `succeeded`

These labels are API-level truth for read-side consumers. Do not rename or add new states lightly.

## Write-side vs Read-side

- **Write-side model**: pipeline/DAG normalizes execution outcomes and persists canonical run facts in `run_results.json` first.
- **Read-side model**: UI/report consumers load typed run context and project statuses through one canonical projection path.

Persistence order:

1. Canonical outcome record (`run_results.json`)
2. Artifact registration (`manifest.json`)
3. Secondary summaries/projections

## Projection Rules

Read-side status projection is implemented in `run_outcome_truth.py`.

High-level rules:

- `modules_run` -> `succeeded`
- `modules_skipped[].execution_status == blocked` -> `blocked`
- `modules_skipped[]` otherwise -> `skipped`
- `modules_failed` -> `failed`
- `modules_enabled` entries not otherwise classified -> `enabled`
- entries present in run lists but not enabled set -> `requested`

## Cache Semantics

Cache-hit is represented as metadata, not a separate status:

- status remains `succeeded`
- `used_cache: true`
- optional reason code `cache_hit`

This keeps terminal status stable while preserving freshness provenance.

## Loader Contract

Consumers should use typed loader paths:

- `load_run_results(...)`
- `load_run_outcome_context(...)`

Avoid raw ad-hoc `json.loads` for canonical truth-path consumption.

## Partial v2 payloads vs old schema versions

Typed loaders **do not** accept `run_results.json` with `schema_version < 2`. `load_run_results(...)` calls `assert_run_results_schema_supported`, which requires **`schema_version >= 2`** (`transcriptx.core.pipeline.module_outcomes`); older on-disk summaries must be regenerated by re-running analysis.

After that gate, `load_run_results` may apply **defaults for missing optional fields** (for example empty lists or placeholder `run_id` / `transcript_key` values). That “partial v2” behavior is not the same as loading schema v1 files.

**Read-side heuristics** in reporting or discovery (for example inferring status from files on disk when `run_results` is missing) are **not** canonical execution truth—they assist operators only. Canonical status projection remains `run_results` + `run_outcome_truth`.

## Decision Log Anchors

When semantics are ambiguous, log explicit decisions for:

- blocked vs skipped precedence
- cache-hit interpretation
- partial `run_results` with manifest present
- group/member status rollups

## Group Truth Projection

Group runs use a projection-over-truth model:

- Group `run_results.json` is the canonical persisted **group-module rollup**.
- Member `run_results.json` files are the canonical **member execution detail**.
- Read-side group consumers combine both through `project_group_outcomes(...)`.

`project_group_outcomes(...)` derives group status using deterministic predicates:

- `any_member_usable`
- `group_phase_terminal_failure`
- `all_members_blocked`
- `all_members_skipped`

This keeps `failed` / `partial` semantics auditable and prevents local heuristics.

Group phase metadata is currently persisted in `aggregation_warnings.json`. The
typed loader/API uses neutral naming (`load_group_phase_metadata(...)`) so the
read-side contract remains stable if the file name evolves.
